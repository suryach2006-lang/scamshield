1. PROJECT PURPOSE
--------------------------------------------------------------------------------
- What ScamShield does:
  ScamShield is an evidence-based recruitment and job offer fraud intelligence
  platform. It takes job listing attributes (company name, job title, job URL,
  salary, location, recruiter contacts, and full job description), gathers live
  multi-engine search evidence via SerpApi (Google Web, Google Jobs, Google News),
  evaluates the listing against 10 deterministic heuristic warning rules, and
  presents an objective risk assessment. It strictly avoids generating synthetic
  AI percentages or hallucinated claims.

- Main user flow:
  1. User fills the inspection form (or clicks a 1-click preset demo).
  2. User clicks "Analyze Job".
  3. The app transitions to a dedicated "Analyzing" screen showing an active
     5-stage progress indicator.
  4. Backend executes targeted SerpApi searches, normalizes evidence, and runs
     deterministic threat rules.
  5. The app transitions to a dedicated "Results" view presenting an executive
     summary, detected warning indicators, compact evidence categories, employer
     verification signals, and candidate precautions.
  6. The completed analysis is automatically saved to MongoDB.
  7. When the user returns to the form via "[New Analysis]", the scan appears in
     "Recent Scan History" and can be reopened instantly without re-querying SerpApi.

3. FRONTEND
--------------------------------------------------------------------------------
- Framework/library:
  React 19, Vite 8, Lucide React (icons), Vanilla CSS design token system
  (no Tailwind, no third-party UI component libraries).

- Main pages/components:
  - App.jsx: State coordinator managing views ('form' | 'analyzing' | 'results'),
    browser history (popstate), and scan auto-save triggering.
  - Header.jsx: Brand title, tagline, dark/light mode toggle, engine health status.
  - JobForm.jsx: Input fields + 1-click test presets (Fee Scam, Spoof Scam, Legit Job).
  - AnalyzingScreen.jsx: Dedicated progress view with horizontal progress bar and
    5 active inspection checklist stages.
  - ResultsView.jsx: Dedicated report page with top navigation toolbar, target info,
    and structured assessment sections.
  - EvidenceHub.jsx: Compact 3-category investigation grid (Company Web, Google Jobs,
    News & Fraud Intel) with on-demand "[View Evidence]" expandable detail drawers.
  - RecentScans.jsx: Card grid under inspection form displaying previous scans with
    role, company, date, risk badge, and "[Open Report ->]" trigger.
  - SummaryCard.jsx: Executive threat assessment badge and 4-metric tally grid
    (Critical, High, Moderate, Minor).
  - RiskIndicatorsSection.jsx: Warning signal cards with severity badges and
    collapsible matched evidence quote snippets.
  - VerificationSignalsSection.jsx: Compact 2-column split (Verified vs Missing)
    with on-demand detail drawers.
  - RecommendationsCard.jsx: Actionable candidate safety steps.
  - ErrorAlert.jsx: Error banner with retry trigger.

- How the user interacts with the app:
  Users enter listing details or click presets, submit for live analysis, observe
  the analyzing stage tracker, review the concise results summary, expand detailed
  evidence drawers as needed, and revisit previous scans from the recent history grid.

- Current UI/UX flow:
  Strict 3-stage lifecycle: FORM -> ANALYZING -> RESULTS.
  Results never render underneath the form. Navigation supports browser back
  and forward buttons via popstate.

- Theme / dark-light mode:
  Fully implemented using CSS custom properties (:root, [data-theme="dark"] and
  [data-theme="light"]). Toggled from the header, persisted via localStorage
  ('scamshield_theme'), with zero-flash pre-mount script in index.html.


4. BACKEND
--------------------------------------------------------------------------------
- Node/Express structure:
  Standard layered architecture: Routes -> Controllers -> Services -> Models.

- Important routes:
  - GET  /api/health      : Backend health telemetry (status, uptime, timestamp)
  - POST /api/analyze     : Live listing analysis through rule engine and SerpApi
  - POST /api/scans       : Save completed analysis scan to MongoDB
  - GET  /api/scans       : Retrieve recent scan summaries (?limit=N)
  - GET  /api/scans/:id   : Retrieve full analysis scan by ID
  - GET  /api/search/web  : Direct Google web search proxy
  - GET  /api/search/jobs : Direct Google Jobs search proxy
  - GET  /api/search/news : Direct Google News search proxy

- Controllers:
  - analyzeController.js : Validates listing input and runs analysisService.
  - scanController.js    : Validates scan payloads, handles Mongoose CRUD, and
                           manages fallback caching.
  - healthController.js  : System metrics provider.
  - searchController.js  : Validation for raw search proxies.

- Services:
  - analysisService.js             : Top-level analysis orchestrator.
  - serpApiService.js              : Low-level SerpApi SDK client.
  - serpApiIntelligenceService.js  : Targeted query constructor with 3-query budget.
  - ruleEngine.js                  : Dynamic runner executing 10 warning rules.

- Middleware:
  - notFoundHandler.js : Returns 404 JSON for unmatched routes.
  - errorHandler.js    : Centralized error handling returning structured JSON errors.

- How frontend communicates with backend:
  Frontend calls relative /api/* paths via native fetch in scamShieldApi.js.
  Vite reverse-proxies /api requests to http://localhost:5000 in development.


5. SERPAPI
--------------------------------------------------------------------------------
- Where SerpApi is integrated:
  server/services/serpApiService.js (wrapper around official serpapi package) and
  server/services/analysis/serpApiIntelligenceService.js (intelligence gathering).

- Which searches are currently used:
  1. Google Web Search (engine: "google"):
     Query: '"{companyName}" official site OR careers'
     Used to corroborate official company domain, Knowledge Graph, and legitimate portals.
  2. Google Jobs Search (engine: "google_jobs"):
     Query: '"{jobTitle} {companyName}"' (+ location)
     Used to corroborate active listings syndicated across indexed job boards.
  3. Google News Search (engine: "google_news"):
     Query: '"{companyName}" (scam OR fraud OR fake OR fake offer OR arrest)'
     Used to detect public cybercrime advisories, police FIRs, or impersonation reports.

- How the API key is loaded:
  Read exclusively on the backend via process.env.SERPAPI_KEY from server/.env.
  The key is never exposed to the client, never logged, and never stored in MongoDB.

- How data flows:
  Frontend sends listing payload -> Backend builds 3 targeted queries -> Backend
  calls SerpApi SDK -> SerpApi returns raw Google JSON -> Backend normalizes data
  (stripping excess fields) -> Normalized evidence feeds into rule engine ->
  Combined evidence and indicators returned to frontend.


6. ANALYSIS LOGIC
--------------------------------------------------------------------------------
- How job information is analyzed:
  Payload is normalized by normalizer.js into structured fields. The rule engine
  runs 10 deterministic heuristic rules against the input and SerpApi evidence.
  calculateAssessment() computes the final threat level based on indicator counts:
  HIGH_RISK, ELEVATED_RISK, MODERATE_RISK, LOW_RISK, or INSUFFICIENT_DATA.

- What warning indicators are detected (10 REAL implemented rules):
  1. upfrontPaymentRule        : Demands for registration fees, training fees, kit deposits.
  2. employmentPaymentRule     : Paying money to obtain employment, wallet recharge schemes.
  3. sensitiveFinancialRule    : Asking for OTP, net banking password, ATM PIN, blank cheques.
  4. unrealisticCompensationRule: Absurd pay (e.g. ₹6,000/day) for low-skill/minimal hours.
  5. contactChannelRule        : Contact exclusively via Telegram/WhatsApp or public webmail.
  6. domainMismatchRule        : Stated company domain mismatches recruiter email domain.
  7. urgencyGuaranteedRule     : "Direct joining without interview", guaranteed selection.
  8. taskScamRule              : Liking YouTube videos, rating Google Maps, task commissions.
  9. suspiciousUrlRule         : URL shorteners (bit.ly) or direct chat invite links.
  10. missingVerificationRule  : Missing legal entity name, generic labels ("Reputed MNC").

- How evidence is presented:
  - Verified Signals (positive markers confirmed by external records).
  - Missing Signals (expected corporate signals not found).
  - Multi-engine evidence cards with direct links to sources.

- Real vs Placeholder:
  - REAL: All 10 deterministic rules, input normalizer, SerpApi query generator,
    zero-result handling, risk assessment calculation, and evidence extraction.
  - NOT IMPLEMENTED (PLANNED): Automated PDF offer letter parsing, standalone UPI
    VPA lookup, automated WHOIS domain registration age verification.


7. MONGODB
--------------------------------------------------------------------------------
- Whether MongoDB is currently implemented:
  Yes, fully implemented using Mongoose.

- Connection method:
  Mongoose v9.11.0 via mongoose.connect() inside server/config/db.js.
  Connects to process.env.MONGODB_URI or mongodb://127.0.0.1:27017/scamshield.

- Database and Collection:
  Database: scamshield
  Collection: scans

- Schema / Model (server/models/Scan.js):
  - input: companyName, jobTitle, jobUrl, jobDescription, salary, location, recruiterContact
  - results: summary (assessment, headline, indicatorCounts, disclaimer, recommendations),
             riskIndicators, webEvidence, jobEvidence, newsEvidence, verificationSignals,
             metadata (analyzedAt, executionDurationMs, serpApiRequestsMade)
  - createdAt: Timestamp generated via Mongoose timestamps option.

- What gets saved:
  User-provided input details and completed analysis findings. No secrets or API keys.

- How scan history is retrieved:
  - GET /api/scans?limit=N returns lightweight summary projections sorted by createdAt descending.
  - GET /api/scans/:id returns the complete scan document with all evidence.

- Current status:
  WORKING. Features a transparent in-memory fallback cache so that if a local MongoDB
  daemon is offline in development, scan saving and retrieval continue functioning.
